# XR-DAP 链路帧与 XR 厂商扩展

[English](protocol.en.md)

本文说明 XR-DAP 系列探针（XRDAP-ESP、XRDAP-F103C8、XRDAP-CH32V3）与上位机之间的协议：XRDAP-ESP 在串口和 TCP 上传输 CMSIS-DAP 包时使用的帧格式，全系列都实现的 XR 厂商扩展命令（协议版本 2；0x80 到 0x85 为数据命令；0x86 为 Wi-Fi 配置，仅 XRDAP-ESP）和探针一次只使用一条链路的规则，探针的身份信息和 mDNS 广播，ESP32-C3 的 USB 口上 DAP 链路与命令行的分流，`xrdap share usbip` 提供的 USB/IP 虚拟设备，USB 主机要注意的零长度包，以及两块无线探针之间的链路。USB 上的 DAP 包按 CMSIS-DAP v2 的 Bulk 端点收发，没有额外的帧。这些规则在本仓库的 `xrdap/` 里实现：串口帧在 `xrdap/serial/`，执行器在 `xrdap/session/`，控制口在 `xrdap/control/`，厂商扩展在 `xrdap/vendor/`，无线链路在 `xrdap/radio/`。

目录：1 串口帧；2 TCP 帧；3 XR 厂商扩展（3.1 规则与一次只使用一条链路，3.2 状态与回复空间，3.3 条目，3.4 命令，3.5 采样，3.6 SWD 访问，3.7 0x86，3.7.1 控制口，3.8 字节示例）；4 探针身份与发现（DAP_Info、mDNS）；5 ESP32-C3 的 USB 口；6 USB/IP 虚拟设备；7 USB 主机的注意事项；8 两块探针之间的无线链路（8.1 包，8.2 会话，8.3 控制口操作，8.4 信道）。

所有整数都是小端。十六进制示例中的空格只为易读。

## 1. 串口帧

串口帧与 libxr 的 Topic 打包帧格式相同。固件端由本仓库的 `xrdap/serial/`（`Framer` 拼帧、`SerialLink` 收发）实现，电脑端由 XRDAP-Host 的 `xrdap` 库（`transport::serial`）实现。

```
prefix 0x5A(1) + data_len(3) + topic_crc32(4) + timestamp_us(6) + version(1) + header_crc8(1) + payload(data_len) + crc8(1)
```

| 字段 | 内容 |
|---|---|
| prefix | 固定 `0x5A` |
| data_len | payload 的字节数，24 位 |
| topic_crc32 | topic 名的 CRC32。请求 topic 为 `dap_req`（`0xDC8309C5`），响应 topic 为 `dap_resp`（`0x89E1A688`） |
| timestamp_us | 48 位。探针在响应里填自己的微秒时间；请求填 0，探针不读取 |
| version | 固定 `0x01` |
| header_crc8 | 前 15 字节的 CRC8 |
| payload | `n(2) + DAP 包(n)`，n 为 DAP 包的字节数，不补零 |
| crc8 | 帧头和 payload 的 CRC8 |

CRC8 为反射多项式 `0x8C`、初值 `0xFF`；CRC32 为反射多项式 `0xEDB88320`、初值 `0xFFFFFFFF`、结果不取反（`"123456789"` 的值为 `0x340BC6D9`）。

例：请求 `DAP_Info(0xFF)`（查询包长，DAP 包为 `00 FF`）的完整帧：

```
5A 04 00 00 C5 09 83 DC 00 00 00 00 00 00 01 B1 02 00 00 FF 32
```

探针按以下规则解析：

- 帧长是 64 的整数倍的帧后面跟一个 0x00 补位字节；接收方丢掉 0x5A 之前的字节。USB 转串口（CP210x、CH343、USB Serial/JTAG）把数据按 64 字节的全速 bulk 包发给主机，刚好填满整包的数据要等下一个短包到来才交给主机程序，补位字节让最后一个包变短。探针发出的响应帧按此补位。
- 帧头 CRC8 错、version 不是 1、topic 不是 `dap_req`、data_len 小于 2 或大于 2 + 包长（DAP_Info 报告的包长）时，丢弃当前候选帧，从缓冲里的下一个 `0x5A` 重新开始解析。
- 尾 CRC8 错时同样丢弃并重新同步。
- n 大于包长或 n + 2 大于 data_len 时丢弃该帧，不回响应。
- 被丢弃的请求没有响应，由上位机按超时处理。`xrdap share` 在响应超时（`--timeout-ms`，默认 2000 ms）内等不到探针的响应，或与探针之间的串口、USB、TCP 读写出错时，结束这个调试工具的连接并报告原因。`DAP_TransferAbort`（0x07）照常转给探针，按 CMSIS-DAP 没有响应，`xrdap share` 不向调试工具回任何内容；经串口时探针回的 n 为 0 的帧由上位机丢掉。

请求和响应一一对应。上位机每次发一个请求，收到响应后再发下一个。没有响应内容的命令，响应帧的 n 为 0。

固件的波特率为 4 000 000（XRDAP-ESP 的 S2、S3 版 `firmware/esp32sx/main/config.hpp` 的 `kSerialBaud`；C3 版走 USB Serial/JTAG，波特率不起作用；传统 ESP32 版受板上 USB 转串口芯片限制为 921 600，见 `firmware/esp32/main/config.hpp`），8 位数据、无校验、1 位停止位、无流控。

串口没有连接和断开的概念。连接在串口上时，5 秒内没有任何请求，连接就作废，见 3.1 节。

## 2. TCP 帧

探针的 TCP 3241 端口和 `xrdap share openocd` 的监听端口使用同一种帧，与 OpenOCD 的 `cmsis-dap backend tcp` 一致：

```
"DAP\0"(4) + 长度(2) + 类型(1) + 保留(1) + DAP 包
```

类型为 1 表示请求，2 表示响应，3、4 是控制请求和控制应答（3.7.1 节）；保留字节填 0。长度是后面 DAP 包的字节数。

- 同一时间只服务一个客户端，请求按顺序执行并应答。客户端断开时结束 TCP 的会话（3.1 节）。
- 探针收到的帧头无效（magic 不对、类型不是 1 或 3、长度为 0 或大于 1024）时关闭连接。
- 没有响应内容的命令（例如 `DAP_TransferAbort`）不回 TCP 帧。
- `xrdap share openocd` 把 TCP 帧去掉 8 字节头后交给探针（经串口时换成串口帧），响应反向转换，不解析 DAP 内容。客户端断开后，它向探针发送一次 `84 00`（停止采样）。

## 3. XR 厂商扩展

本节是协议版本 2，不兼容版本 1：版本 1 的 SUB_SET 和 SUB_CTRL 开始已经合并为 SUB_START，INFO 不再报告访问耗时。上位机先发 INFO，版本不是 2 时不使用扩展。

### 3.1 规则

- 命令放在 CMSIS-DAP 的厂商命令区：0x80 到 0x85 为数据命令（3.2 到 3.6 节），0x86 为 Wi-Fi 配置（3.7 节，仅 XRDAP-ESP）。USB、TCP、串口、无线使用同一种包。
- 探针不支持的命令响应只有一个字节 `0xFF`，这是 CMSIS-DAP 的标准行为。上位机发送 INFO 得到 `FF` 时，即可判断探针没有实现扩展。
- 只支持 SWD。目标按小端处理，数值就是目标内存里的原始字节。
- 变量地址由上位机解析（符号表、DWARF），探针只处理地址。
- 使用扩展命令前，上位机要先用 `DAP_Connect` 以 SWD 方式连接（port 为 0 或 1），并确认目标可访问。探针不替上位机连接；本会话里还没有连接时，READ、WRITE、SUB_START 返回 0x04。`DAP_Disconnect` 或会话结束之后都要重新 `DAP_Connect`。
- 用过 READ、WRITE 或采样之后，上位机必须把 DP SELECT、AP CSW、TAR 当作未知，重新写入。OpenOCD 会缓存这些寄存器，所以扩展命令和 OpenOCD 不在同一个连接里混用。

#### 一次只使用一条链路

探针一次只使用一条链路（USB、串口、TCP、无线远端）由使用者保证，探针不仲裁：没有会话主人、没有排队，也不再回“忙”。所有命令谁发都执行；两条链路同时发命令时，探针一次只执行一条，别的等着，顺序不保证先来先到：USB 的命令优先，别的链路的命令要等到没有 USB 命令等着时才执行，可能要等过好几条，这些链路之间轮流。同时使用时 SWD 状态可能被弄乱。

`DAP_Connect`（port 为 0 或 1）记下它来自哪条链路，这个连接在以下情况作废，之后扩展命令要求重新 `DAP_Connect`，正在进行的采样停止：

| 情况 | 作废的连接 |
|---|---|
| 发出 `DAP_Disconnect`（采样进行中这条命令被拒绝，回 `FF`） | 任何链路上的连接 |
| TCP 客户端断开、串口链路停止 | 连接在这条链路上时 |
| 5 秒内没有收到任何串口请求 | 连接在串口上时 |
| USB 总线复位（拔出或主机复位） | 连接在 USB 上时 |
| 无线会话号变化或为 0，或超过租期没有 ping | 连接在无线远端上时（XRDAP-CH32V3） |

连接不在丢失的那条链路上时，什么也不发生。

采样进行中，开始采样的那条链路又发来 `DAP_Connect`：视为它的上位机回来了（旧的没发 `DAP_Disconnect` 就没了，例如被强杀），探针结束旧的连接和采样并重新连接。别的链路的 `DAP_Connect` 仍回 `FF`（采样期间只放行 `DAP_Info`、`DAP_HostStatus` 和厂商命令）。

串口作为连接所在的链路时，上位机要至少每 5 秒发一个请求（SUB_READ 即可）。

USB 的连接和断开（主机打开或关闭 USB、重新枚举）只属于 USB 自己：只有连接在 USB 上或没有连接时，探针才因此复位 SWD 和 DAP 的状态；连接在别的链路上时，它的 SWD 连接、时钟和设置都不变。

上位机退出时应发 `DAP_Disconnect`（XRDAP-Host 会这样做）：Windows 上关闭 USB 设备不会产生任何 USB 事件，探针只能靠这条命令知道连接结束。

`DAP_ExecuteCommands` 里前面的命令用掉了包里的空间，轮到 READ 时只剩 5 字节，而它的回复要 10 字节：这条 READ 的回复为 `81 03`，不执行。只剩 1 字节时为 `FF`。

#### 采样

采样归开始它的会话所有：

- 从开始采样到停止，只接受 `DAP_Info`（0x00）、`DAP_HostStatus`（0x01）和 0x80 到 0x86。其他命令一律只回一个字节 `0xFF`，不执行。
- READ、WRITE 在采样期间可以使用，它们和采样轮流占用 SWD，可能使采样出现跳拍。
- 采样在收到 SUB_CTRL 停止（`84 00`）或开始它的会话结束时停止。停止后缓冲里的帧保留，下一个会话仍可以用 SUB_READ 读走，直到下一次 SUB_START 或清空。

### 3.2 请求、响应和状态

请求为 `命令字节 + 参数`；响应为 `命令字节 + 整体状态 + 数据`，命令字节原样回显。整体状态不为 0 时响应只有这两个字节，SUB_READ 的 0x02 除外（见 3.4 节）。

请求长度与命令里的计数字段对不上时返回 0x01，不执行。

回复空间：每条厂商命令执行前，探针先按请求算出回复要多少字节，与这一次能写的空间比较。空间是 DAP_Info 报告的包长（XRDAP-ESP 和 XRDAP-CH32V3 为 1024 字节，XRDAP-F103C8 为 512 字节）；在 `DAP_ExecuteCommands` 里是这个包里还没用掉的部分。厂商命令可以放进 `DAP_ExecuteCommands` 和 `DAP_QueueCommands`，与 CMSIS-DAP 参考实现相同；容器里的命令首尾相接，每条的长度由它自己的内容得出（READ、WRITE、SUB_START 按条目数和条目，INFO 1 字节，SUB_CTRL 2，SUB_READ 3，0x86 按操作：查询 2、保存 3 + ssid_len + 1 + pw_len、清除 3），算不出长度的容器整个回 `7F FF`。空间不到 2 字节时只回一个 `FF`；放不下整条回复时回 `命令号 03`；两种情况都不执行，也不写出给定的空间。READ 的回复为 3 + Σ(3 + size) 字节，WRITE 为 3 + 3 × count，INFO 为 22，SUB_START、SUB_CTRL 为 2，SUB_READ 至少 24。

| 整体状态 | 含义 |
|---|---|
| 0x00 | 成功；各条目的结果看条目状态 |
| 0x01 | 参数非法：长度对不上、计数为 0、size 不是 1/2/4/8、解引用次数大于 8、period 为 0、div 为 0 或 phase ≥ div、flags 保留位非 0、SUB_CTRL 的 op 未定义 |
| 0x02 | 状态不允许：采样中再发 SUB_START；SUB_READ 时没有在采样（回复照样带数据） |
| 0x03 | 资源不足：条目数超过 32、回复放不进剩余空间、一次采样用到超过 8 个不同的 AP、所有条目都到期的一帧放不进缓冲 |
| 0x04 | 没有连接目标：本会话还没有 `DAP_Connect`，或读取 AP 的 CSW 失败 |
| 0x05 | 忙：保留的值，当前固件不再发出（3.1 节） |

条目状态（READ、WRITE 的每个条目一个字节；采样帧里只用 1 位表示成功或失败）：

| 条目状态 | 含义 |
|---|---|
| 0x00 | 成功 |
| 0x10 + k | 第 k 级（0 到 7）读指针时 SWD 返回 FAULT 或超时 |
| 0x1F | 最后一次读或写时 SWD 失败（包括写后检查到粘滞错误） |
| 0x20 + k | 第 k 级的读地址没有 4 字节对齐 |
| 0x2F | 最后访问的地址没有按 size 对齐（size 为 8 时要求 4 字节对齐） |
| 0x30 + k | 第 k 级读出的指针为 0，不再继续 |

### 3.3 条目

一个条目描述一个变量的位置，可以经过最多 8 级指针。

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | ap：MEM-AP 编号 |
| 1 | 2 | id：上位机自定，响应里原样带回 |
| 3 | 1 | size：1、2、4 或 8 |
| 4 | 4 | base：起始地址 |
| 8 | 1 | n：解引用次数，0 到 8 |
| 9 | 2×n | deref_off[i]，i16，i = 0 到 n-1 |
| 9+2n | 2 | final_off，i16 |

条目长度为 11 + 2n 字节。WRITE 的条目后面紧跟 size 字节的值；采样条目后面紧跟 `div(2)` 和 `phase(2)`；READ 的条目没有额外字段。

探针按以下步骤求出最终地址：

```
cur = base
for i in 0..n-1:
    addr = cur + sign_extend(deref_off[i])      // 32 位回绕
    addr 不是 4 的倍数     -> 条目状态 0x20+i，结束
    p = read32(addr)                             // SWD 失败 -> 0x10+i，结束
    p == 0                 -> 条目状态 0x30+i，结束
    cur = p
addr = cur + sign_extend(final_off)
addr 不是 size 的倍数（size 为 8 时按 4） -> 0x2F，结束
读或写 size 字节                                  // SWD 失败 -> 0x1F
```

n 为 0 时直接访问 `base + final_off`。base 为 0 是合法的（Cortex-M 的 0 地址有效），只有读出来的指针为 0 才算空指针。数组下标和链表遍历由上位机展开成多个条目。

### 3.4 命令

#### 0x80 INFO

请求：`80`

响应固定 22 字节：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x80 |
| 1 | 1 | 整体状态 |
| 2 | 1 | 协议版本，当前为 2 |
| 3 | 4 | 功能位：bit0 READ，bit1 WRITE，bit2 采样，bit3 8 字节访问，bit4 Wi-Fi 配置（0x86），bit5 有控制口（3.7.1），bit6 支持紧凑帧（3.5）；XRDAP-ESP 为 0x7F，XRDAP-CH32V3 为 0x6F，XRDAP-F103C8 为 0x4F（不支持紧凑帧的旧固件分别为 0x3F 或 0x1F、0x2F、0x0F） |
| 7 | 2 | 一个请求或一次采样最多的条目数：32 |
| 9 | 1 | 最大解引用深度：8 |
| 10 | 4 | 环形缓冲字节数：XRDAP-ESP 为 16384（ESP32-S2 为 4096），XRDAP-F103C8 和 XRDAP-CH32V3 为 4096（CH32V305 和 CH32V208 板为 2048） |
| 14 | 8 | 探针当前时间，µs |

#### 0x81 READ

请求：`81 count(1) item…`，count 为 1 到 32。

响应：`81 状态 count(1)`，然后每个条目 `id(2) 条目状态(1) value(size)`。失败的条目 value 全为 0。

#### 0x82 WRITE

请求：`82 count(1) (item value)…`，value 为 size 字节，按目标字节序。

响应：`82 状态 count(1)`，然后每个条目 `id(2) 条目状态(1)`。

条目按顺序执行，已经写入的不回滚，某个条目失败不影响后面的条目。8 字节写是两次 32 位写，不是原子的。

#### 0x83 SUB_START

一条命令带全部配置，检查通过就开始采样。探针不保存“已配置未开始”的状态。

请求：`83 period_us(4) flags(1) count(2) (item div(2) phase(2))…`

- period_us：节拍周期，大于 0。
- flags：bit0 为 0 时缓冲满后覆盖最旧的帧，为 1 时丢弃新帧；bit1 为 1 时 SUB_READ 用紧凑帧（3.5 节，探针的 INFO 功能位 bit6 为 1 时才能用，不支持的探针回 0x01）；其余位必须为 0。
- count：1 到 32。

响应：`83 状态`

- 采样中再发 SUB_START 返回 0x02，正在进行的采样不受影响。
- 参数非法返回 0x01；条目超过 32 个、用到超过 8 个 AP、所有条目都到期的一帧加 2 字节长度头大于缓冲时返回 0x03。
- 本会话没有 `DAP_Connect`，或读某个 AP 的 CSW 失败返回 0x04。
- 成功时清空缓冲和两个计数器，节拍序号从 0 开始，第 0 拍立即采样。

探针不估计每帧耗时，也不因为周期太短拒绝。能否跟上只在运行时看：跳过节拍数、缓冲丢帧数和缓冲里剩余的字节数，都在每次 SUB_READ 的响应头里（3.5 节）。

#### 0x84 SUB_CTRL

请求：`84 op(1)`；op 为 0 停止，2 清空缓冲和计数器。其他 op 返回 0x01。

响应：`84 状态`

- 停止：等手头这一拍读完再回复，没有在采样时也返回 0x00。缓冲里的帧可以继续用 SUB_READ 读走。
- 清空：采样中也可以用，计数器从 0 重新累计。

#### 0x85 SUB_READ

请求：`85 max_bytes(2)`

响应头 24 字节，后面是帧：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x85 |
| 1 | 1 | 整体状态：0x00 正在采样，0x02 没有在采样 |
| 2 | 8 | 探针当前时间，µs |
| 10 | 4 | 缓冲里剩余未取的帧字节数（不含长度头） |
| 14 | 4 | 累计缓冲丢帧数 |
| 18 | 4 | 累计跳过节拍数 |
| 22 | 2 | 本次返回的帧数 |
| 24 | … | 帧 |

只返回完整的帧，帧的总长不超过 `min(max_bytes, 回复空间 - 24)`，紧凑帧按编码后的长度算；缓冲为空时帧数为 0。状态为 0x02 时响应照样带完整的头和帧：上位机据此知道采样已经停止（例如开始它的会话结束了），继续读到剩余字节为 0 即可。两个计数器在 SUB_START 成功和 op 2 时清零。

### 3.5 采样

#### 节拍

- 节拍定时器是唯一的时钟。它的中断每个周期把节拍计数加 1，计数到达下一个要采的节拍时才唤醒采样；采样醒来时读计数，最新的节拍就是计数值 k。时基只用来给帧打时间戳。
- SUB_START 成功后计数清零，第 0 拍立即采样，此后每过一个周期一拍。
- 条目在 `(k + phase) % div == 0` 的拍被采样。div 为 1 表示每拍都采；phase 用来错开慢速条目。一拍里到期的条目按 SUB_START 中的顺序依次读取。
- 没有条目到期的拍不产生帧。

#### 帧格式

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 4 | 节拍序号 k |
| 4 | 6 | 时间戳，µs，在该拍开始读取时取得 |
| 10 | ceil(m/8) | 状态位图，m 为到期条目数；第 i 个到期条目对应第 i 位（低位在前），1 表示失败 |
| … | … | 各到期条目的值，按到期顺序，每个 size 字节，失败时全为 0 |

到期的条目由 k 和各条目的 div、phase 推算，帧里不重复列出。

#### 紧凑帧

SUB_START 的 flags bit1 为 1 时，SUB_READ 的帧改用紧凑编码，直到下一次 SUB_START。只改回复里的编码，缓冲里存的仍是上面的完整帧，缓冲大小、覆盖和丢弃、剩余字节数（按完整帧计）都不变。

- 每个回复的第 1 帧是完整帧，格式同上。每个回复单独解码，不依赖上一个回复。
- 之后每帧：

| 字段 | 大小 | 内容 |
|---|---|---|
| h | 变长 | `(Δk << 1) \| f`：Δk 为本帧节拍序号减回复里上一帧的节拍序号（至少 1；跳拍、丢帧后大于 1）；f 为 1 表示有到期条目失败 |
| Δt | 变长 | 本帧时间戳减上一帧时间戳，µs，按 48 位回绕 |
| 位图 | ceil(m/8) | 只在 f 为 1 时出现，含义同完整帧；f 为 0 表示到期条目全部成功 |
| 值 | … | 同完整帧 |

- 变长字段为无符号 LEB128：每字节低 7 位，从低位起；最高位为 1 表示后面还有字节。
- 每拍采一次、全部成功、周期 1 ms 时帧头为 3 字节（完整帧为 11 字节）：1 个 4 字节条目的帧从 15 字节降到 7 字节，8 个从 43 降到 35，32 个从 142 降到 134。

- 时间戳取自 libxr 的 Timebase，是探针的单调微秒时间，48 位，与 INFO、SUB_READ 里的探针当前时间是同一个时钟。每次开始采样时时间轴不重置，节拍序号从 0 重新计；探针重启后时间轴从 0 开始。
- 一帧内的条目依次读取，同一帧的变量之间有时间差，不是同一时刻的值。
- 对齐到上位机时钟：记下 INFO 或 SUB_READ 请求前后的本机时间，取中点与响应里的探针当前时间配对，得到偏移量，误差约为半个往返时间。每次 SUB_READ 都可以顺便更新偏移量。

#### 跟上与跳拍

- 采样醒来时，从上一次采到的节拍到当前计数之间没有采的节拍都算跳过，累计到跳过节拍数；节拍序号因此出现缺口。探针不补做，也不自动降频或去掉条目。
- 一拍读到一半时下一个节拍已经到了，这个节拍不补做，等再下一个节拍。
- 每帧读完后，下一个要采的节拍至少比这一帧的节拍晚 `占用 + 间隙`，间隙为 `max(15 µs, 周期 / 8, 占用 / 4)`，占用从开始读这一帧算到读完；中间的节拍计入跳过节拍数。
- 命令和采样在同一个执行上下文里轮流进行：一轮最多采一帧，采完回头先看有没有命令（USB 的、别的链路投来的）。所以一条命令最多被采样占一帧，与周期无关；采不过来的节拍计入跳过节拍数。命令和采样不重叠时没有影响，定时的 SUB_READ 不会因此多出跳拍。
- 因此任何周期下探针都能回应命令：两帧之间同一个核上的其他任务（DAP 命令、串口、TCP）至少有这段间隙，约占这个核 1/5 以上的时间。周期短于一帧的占用时只多出跳过的节拍，命令不会等不到 CPU。

#### 读取太慢

帧先写进环形缓冲（大小见 INFO，每帧另占 2 字节长度）。缓冲满时按 flags.bit0 覆盖最旧的帧或丢弃新帧，覆盖或丢弃的帧数累计到缓冲丢帧数，节拍序号的缺口也能看出丢了哪几拍。剩余未取字节数不为 0 时，上位机应立即再读。

每拍的字节数为 10 + 位图 + 各到期条目的 size（紧凑帧通常为 3 + 各到期条目的 size），按 div 折算平均值后与链路的实际速度比较，即可估计带宽是否够用。

上位机按这三个量判断能否跟上，并给出建议：

| 量 | 说明 | 建议 |
|---|---|---|
| 跳过节拍数 | 增长说明 SWD 来不及 | 增大周期、增加分频、减少条目 |
| 缓冲丢帧数 | 增长说明读得太慢或链路带宽不足 | 读得更勤、增加分频、减少条目 |
| 剩余字节数 | 持续接近缓冲大小说明快要丢帧 | 同上 |

### 3.6 SWD 访问

- DP SELECT：访问 MEM-AP 时写 `ap << 24`，CSW、TAR、DRW 都在 bank 0。读 AP 的 IDR 时用 bank 0xF（寄存器 0xFC）。
- CSW：每个 READ、WRITE 命令中第一次用到某个 AP 时，以及 SUB_START 时，读一次该 AP 的 CSW；同一命令或同一次采样期间不重新读取。采样活跃时，READ 命令可复用 SUB_START 或先前 READ 读成功的 CSW 基值，仍重新设置访问宽度和自增方式，并且每次都实际读取目标数据；传输失败、重新同步和新采样运行会丢弃该复用。WRITE 始终先清空命令缓存；未在采样时，READ 也仍按每条命令重新读取 CSW。读出的 CSW 里 HPROT1（位 25）为 0 时，再读该 AP 的 IDR：IDR 的类别（位 16:13）为 8（MEM-AP）、类型（位 3:0）为 1、5 或 8（AHB3、AHB5、带增强 HPROT 的 AHB5）时，把 Prot 的位 24（HPROT0，数据访问）、位 25（HPROT1，特权访问）和位 29（调试主机）置 1，与 OpenOCD 的 `CSW_AHB_DEFAULT` 相同；Prot 的其余位（缓存、缓冲、安全属性）保持读出的值。别的 AP 类型（例如 AXI-AP、APB-AP）的这些位含义不同，保持原值。访问时写入 `(上述值 & ~0x37) | Size`，即清掉 Size（位 2:0）和 AddrInc（位 5:4），设置访问宽度并关闭自增。写过一次之后 AP 里的 HPROT1 已经为 1，此后不再读 IDR。
- 读一个字：写 TAR，读 DRW，再读 DP RDBUFF 得到结果。条目按顺序逐个访问。
- 写一个字：写 TAR，写 DRW，再读 DP CTRL/STAT，检查 STICKYORUN、STICKYERR、WDATAERR。
- 1、2 字节访问：CSW 的 Size 设为 8 位或 16 位，值在 DRW 中由地址低位决定的字节通道上，探针把它放到 value 的低字节。
- 8 字节：两次 32 位访问，低地址在前，不是原子的，目标运行时可能读到前后不一致的值。4 字节及以下的对齐访问是单次访问。
- WAIT 应答：沿用 `DAP_TransferConfigure` 设置的重试次数，超过算失败。
- 任何访问出现 FAULT、超时或粘滞错误后，写 DP ABORT = `0x0000001E`（STKCMPCLR、STKERRCLR、WDERRCLR、ORUNERRCLR），再继续下一个条目。
- 读写内存由 MEM-AP 完成，不需要停核。

### 3.7 0x86 Wi-Fi 配置

仅 XRDAP-ESP。经 DAP 本身（USB、串口、TCP 均可）查询、保存、清除热点参数，不需要另开串口终端。INFO 的功能位 bit4 为 1 时才支持。热点参数存放在 NVS 里（命名空间 `rmlink`，键 `wifi`），与串口命令行 `wifi set` 保存的是同一份数据。

这条命令不访问目标，也不要求先 `DAP_Connect`；采样期间同样可用。请求格式为 `86 op(1) 参数`，响应第 1 字节回显 `86`，第 2 字节为状态。

| 状态 | 含义 |
|---|---|
| 0x00 | 成功 |
| 0x01 | 参数非法：op 未定义，请求长度与 op 不符，热点名为空或超过 32 字节，密码不为空且不在 8 到 63 字节之间（WPA 密码长度） |
| 0x03 | 资源不足：NVS 读写失败，或响应缓冲放不下状态响应 |

#### op 0 查询

请求：`86 00`（长度必须为 2 字节）

成功响应：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x86 |
| 1 | 1 | 状态 0x00 |
| 2 | 1 | 标志：bit0 Wi-Fi 已启动（保存了热点参数才会启动），bit1 已拿到 IP，bit2 这次启动时 NVS 已损坏，已擦除重建 |
| 3 | 4 | IPv4 地址，按网络字节序（`C0 A8 01 14` 即 192.168.1.20）；未连接时为 0 |
| 7 | 1 | 信号强度 RSSI，i8，单位 dBm；未连接时为 0 |
| 8 | 1 | 热点名长度 n |
| 9 | n | 已保存的热点名，没有则 n 为 0；不返回密码 |
| 9+n | 1 | 热点参数最近一次被谁清除（存在 NVS 里）：0 没有或不知道，1 板上按键，2 命令行 `wifi clear`，3 0x86 清除，4 NVS 修复 |
| 10+n | 1 | 这次启动的复位原因：0 不知道，1 上电，2 软件重启，3 看门狗，4 程序异常，5 欠压，6 其他 |

失败时响应只有 `86` 和状态两个字节。

#### op 1 保存

请求：`86 01 ssid_len(1) ssid(ssid_len) pw_len(1) password(pw_len)`

请求总长必须等于 `4 + ssid_len + pw_len`。开放网络的 pw_len 为 0。

响应：`86 状态`。状态为 0x00 时热点参数已写入 NVS，响应发出后约 0.5 秒探针重启，重启后用新参数连接热点。重启期间 USB 设备重新枚举，串口和 TCP 连接中断，上位机需要重新连接。

#### op 2 清除

请求：`86 02 A5`（长度必须为 3 字节，第 3 字节是确认字节 0xA5）。确认字节不对或缺少时返回 0x01，什么都不做，防止误发的短命令清掉热点参数。

响应：`86 状态`。状态为 0x00 时热点参数已清除，响应发出后约 0.5 秒探针重启，重启后不启动 Wi-Fi。

### 3.7.1 控制口

设置类请求（上面的 Wi-Fi 操作和 8.3 节的无线操作）不经 DAP，走探针的控制口；Wi-Fi 操作也可以用 `0x86`。请求是 `op(1) + 载荷`，应答是 `op(1) + 状态(1) + 载荷`；Wi-Fi 操作的 `op` 和载荷与 `0x86` 相同，只是请求没有 `86` 字节，应答第 1 字节是 `op`。控制请求由探针的执行上下文与 DAP 命令一件一件处理，没有连接，也不影响 DAP 的连接和采样。探针没有这个操作时应答状态 `0xF2`（控制口自己的“不支持”）；`0xF0` 到 `0xFF` 留给控制口，各探针自己的操作用低位状态码。空请求不算操作：USB 上 SEND 被 STALL，TCP 上帧头无效、连接被关闭（第 2 节），串口上应答 `00 F1`（状态 `0xF1`：请求格式不对）。

| 链路 | 怎么发 |
|---|---|
| USB | 对 DAP 接口发厂商控制传输：`bmRequestType 0x41 bRequest 0x01` 发请求（OUT 数据阶段）；`0xC1 / 0x02` 取应答（IN，应答没好时返回 0 字节，稍后重试）。一次一个请求，取走应答前再发请求会被 STALL；请求不能超过设备 EP0 的 OUT 缓冲（CH32 上是 64 字节，更长的 SEND 被 STALL），主机在 SEND 被拒时要换办法（Wi-Fi 保存请求超过时回退到 `0x86`） |
| 串口 | 同一种帧，topic 换成 `ctrl_req`（`0x3D2538F2`）和 `ctrl_resp`（`0x31BDA5B6`），载荷布局不变（2 字节长度 + 内容）；不续串口的租期 |
| TCP | 同一条连接，帧类型 3 为控制请求、4 为控制应答，其余同第 2 节 |

固件的 `0x86` 仍然保留，新的上位机在有控制口的链路上优先用控制口。

### 4.2 mDNS 广播

探针拿到 IP 后在局域网上广播：

| 项目 | 内容 |
|---|---|
| 主机名 | `xrdap-` 加 MAC 后 3 字节的小写十六进制，例如 `xrdap-6789ab.local` |
| 服务 | `_xrdap._tcp`，端口为 TCP DAP 端口 3241 |
| 实例名 | 序列号，例如 `XRobot-XRDAP-0123456789AB` |
| TXT `serial` | 序列号 |
| TXT `chip` | `esp32s3`、`esp32s2`、`esp32c3` 或 `esp32` |
| TXT `fw` | 固件版本，例如 `0.6.0` |

OpenOCD 可以直接把主机名写进 `cmsis-dap tcp host`。上位机枚举 `_xrdap._tcp` 服务即可列出局域网内的探针，用 TXT 的 `serial` 与 USB、串口上的同一块探针对应。mDNS 启动失败只记日志，不影响 TCP 服务。

## 5. ESP32-C3 的 USB 口

ESP32-C3 的 USB 口是 USB Serial/JTAG，电脑上是一个 CDC 串口，DAP 链路（第 1 节的串口帧）和 Wi-Fi 命令行共用这个口，不需要切换模式。固件（XRDAP-ESP 的 `firmware/common/serial/serial_mux.hpp`）对每块收到的数据这样处理：

1. 先交给 DAP 链路。链路自己查找帧头 `0x5A`、校验 CRC，非帧字节直接丢弃。
2. 这一块数据执行了至少一个 DAP 帧，或者最近 2 秒内执行过 DAP 帧时，数据不交给命令行。
3. 其余数据逐字节交给命令行。命令行只在收到一行人打的命令并以回车结束后才输出；一行里出现控制字符时整行丢弃。

因此 DAP 帧和命令行的输出不会混在一起：调试工具收到的永远是 DAP 响应帧，终端里 `help`、`wifi set` 等命令照常可用。终端不要改动 DTR/RTS，否则 USB Serial/JTAG 可能复位芯片。ESP32-S3 的串口链路在 UART0 上，不做这种分流；它的命令行在 USB 的 CDC 虚拟串口上。

## 6. USB/IP 虚拟设备

探针本身不带 USB 设备模型，只说 DAP（USB、串口、TCP）。电脑上运行 `xrdap share usbip`（上位机 xrdap 库的 `usbip` 模块）后，在 TCP 3240 端口提供 USB/IP（协议见 Linux 内核文档 `usb/usbip_protocol.rst`，字段大端），把任何经串口、TCP 或 USB 连着的探针变成一个 USB CMSIS-DAP v2 探针。设备模型如下。

一个命令引起的回复（OUT 的回复和配上的 IN 响应）合成一次 `send()`。分两次发时，第二段要等对方的延迟 ACK，每个来回都慢很多。

## 7. USB 主机的注意事项

USB 全速的 Bulk 包是 64 字节。请求长度正好是 64 的整数倍（128、192 字节等）、又小于 DAP 包长时，OUT 传输没有短包来标志结束，探针会一直等下去，表现是这个请求没有响应、之后的响应还会错位。主机发完这样的请求后要再发一个零长度包。8 个条目的 SUB_START 正好 128 字节，最容易遇到。`xrdap` 已经处理；自己用 libusb、pyusb 写客户端时要加。接收时 IN 请求的长度要取端点最大包长的整数倍（不小于 DAP 包长）。

## 8. 两块探针之间的无线链路

无线探针成对使用：一块接电脑的 USB（主机），一块接目标（远端），主机把电脑的 DAP 命令经射频发给远端执行，再把应答交回 USB。实现在 `xrdap/radio/`，射频驱动以模板参数传入，要满足 `xrdap/radio/transceiver.hpp` 的契约。不同收发器的探针不能互通。无线链路没有认证：CRC 初值和链路地址只用来把不同的对分开。

### 8.1 包

射频有高、低两档速率，每块板子定义它们的调制和包长（127 到 255 字节）。`wdap` 用 SX1281：高速率是 GFSK，包最长 255 字节；低速率是 FLRC，包最长 127 字节。`linkw` 用 CH32V208 自带的射频：高速率是 2M PHY，包最长 251 字节；低速率是 1M PHY，包最长 127 字节。除 HELLO 外，每个包以 6 字节包头开始：

| 字节 | 内容 |
|---|---|
| 0 | 类型：1 COMMAND，2 ANSWER，3 PING，4 PONG，5 HELLO，6 CONTROL，7 CHANNEL，8 CHANNEL_ACK |
| 1 | 序号；ANSWER、PONG 与对应的请求相同 |
| 2 | 分片序号 |
| 3 | 分片数 |
| 4..5 | 消息总长，小端 |

一条消息（DAP 命令、控制请求或应答）至多 1024 字节，按 fragment = 最大包长 - 6 字节分片：总长 total 的消息分成 max(1, ⌈total / fragment⌉) 片，第 i 片载有第 i × fragment 字节起的至多 fragment 字节。接收方只接受同一（序号、分片数、总长）的所有分片都到齐、每片长度恰好正确的消息。PING、PONG 只有一片，载荷是 2 字节小端会话号。CHANNEL、CHANNEL_ACK 只有一片，载荷是 2 字节小端会话号加 1 字节信道索引（8.4 节）；CHANNEL_ACK 的序号与对应的 CHANNEL 相同。

HELLO 只在配对时使用：`05`、自己的 12 字节芯片 UID、目前听到的对方 UID（还没听到时为 0）。

### 8.2 会话

会话以主机取的 16 位非零会话号命名。主机在会话的第一条命令前发带新会话号的 PING，远端以 PONG 应答；1 s 没有命令时发心跳 PING；`DAP_Disconnect` 或电脑 5 s 没有命令时发会话号为 0 的 PING 结束会话。远端收到会话号为 0 或新的会话号、或 3 s 没有主机的包时结束会话（执行命令的时间不算，命令执行完重新计时），清掉缓存的应答，连接在无线上时连接和采样作废。会话外的 COMMAND 和 CONTROL 不执行、不应答。

主机发出命令后等应答：第一次等 3 ms 加命令的预计执行时间，之后每次重发等待加倍，至多 200 ms，总共至多 1 s 加执行时间；每收到一个应答分片再多等 3 ms。预计执行时间是命令自己的等待（`DAP_Delay`，以及 `DAP_SWJ_Pins` 的等待，后者至多算 3 s）加上它的 SWD 事务按转发过的 `DAP_SWJ_Clock`（还没有时按 500 kHz）算的时间的两倍，`DAP_ResetTarget`、`DAP_QueueCommands` 和 `DAP_ExecuteCommands` 再多算 0.5 s，合计至多 3 s；控制请求按 250 ms 算，对方可能正在写 Flash。远端保留最后一个应答，同序号的命令用缓存应答，不再执行。主机发射时听不到应答，所以远端等这一串分片结束（到了最后一片，或 3 ms 没有下一片）才执行和应答；已拼齐的命令重发时，到了一片就用缓存再答一次。

AUTO 角色下，配对的探针没有自己的会话时当远端；USB 上的 `DAP_Connect` 找到对方时会话走无线，否则在本地执行。`DAP_Connect` 前的 `SWJ_Clock`、`TransferConfigure`、`SWD_Configure` 在本地执行，会话走无线时各重发最后一条给远端。

配对：两块探针都进入配对（至多 10 s）后在控制信道 F 上用默认身份（高速率，链路地址 `XRDP`，CRC 初值 0xFFFF）每 20 ms 左右发 HELLO；听到点了自己 UID 的 HELLO 即完成，再应答 1 s。两块探针由两个 UID 算出同一个链路号，CRC 初值和链路地址由链路号得出；频率见 8.4 节。

### 8.3 控制口操作

无线探针的设置和无线操作走控制口（3.7.1 节）。应答状态：0 成功，1 超时，2 Flash 错误，3 参数错误，4 未配对，5 配对进行中（0x11、0x13 之外的操作要等配对结束）。

| op | 请求载荷 | 作用 |
|---|---|---|
| 0x10 | 角色（0 本地，1 主机，2 远端） | 在下次应用设置前改用这个角色，不保存；未配对时只能设 0 |
| 0x11 | 无 | 无线统计，应答见下表 |
| 0x13 | 无 | 读设置，应答见下表 |
| 0x14 | 角色设置（0 AUTO，1 本地，2 主机，3 远端） | 保存，应答发出后生效 |
| 0x15 | 速率（0 高，1 低） | 保存，应答发出后生效 |
| 0x16 | 无 | 忘掉配对，应答发出后生效 |
| 0x17 | 无 | 引导槽信息（CH32 板） |
| 0x19 | 无，或 mode、信道 | 读信道；mode 0 自动选信道，1 锁定到这个信道（保存，下次选信道时生效）。应答 `19 00`、当前信道、锁定的信道（自动为 0xFF） |
| 0x20 | 无 | 开始配对 |
| 0x30 | 一个控制请求（不能是 0x30） | 经无线发给对方，应答为对方的应答；对方不应答时状态 1。没有无线 DAP 会话时，转发结束后两块探针都回到 F |

0x13 的应答（24 字节）：

| 字节 | 内容 |
|---|---|
| 0..1 | `13 00` |
| 2 | 角色设置 |
| 3 | 速率（0 高，1 低） |
| 4 | 1 已配对 |
| 5 | 1 安全模式（连续看门狗复位后，设置不生效） |
| 6 | 当前角色 |
| 7 | 配对状态：0 空闲，1 进行中，2 完成，3 失败 |
| 8..11 | 链路号，小端 |
| 12..23 | 对方芯片 UID |

0x11 的应答：`11 00 n`，再接 n 个小端 u32（n = 13）：发出的包、收到的好包、坏包、发送失败、转发的命令和控制请求、重发、没等到应答的、远端从缓存应答的、上一条的往返时间（µs）、最长往返时间（µs）、当前信道、射频重新进入接收的次数、射频复位重配的次数。

### 8.4 信道

频点用 0.5 MHz 为单位的信道索引表示：频率 = 2402 MHz + 索引 × 0.5 MHz，索引 0 到 159（2402.0–2481.5 MHz），都在免执照的 2400–2483.5 MHz 内。控制信道 F 是 93（2448.5 MHz），所有探针相同，不同的对靠 CRC 初值和链路地址分开。`wdap` 的 FLRC 同步字固定为 `XRDP`（SX1281 勘误 16.4），低速率下只靠 CRC 初值；`linkw` 两档速率都用链路地址。`linkw` 的信道间隔 2 MHz（2402–2480 MHz），索引落在两个信道之间时取较近的一个。

配对和建立会话都在 F 上。主机在 F 上用 PING 找到对方（`DAP_Connect` 时至多等 300 ms）后选数据信道：锁定的（0x19），或扫描里最好的；第一次建立会话时先扫描（每 1 MHz 一个点，每点 1.5 ms，扫 4 遍、每个点取最差的一遍，约 0.6 s）。忙碌指 RSSI 超过 -85 dBm 的时间占比，选忙碌最低的点，相同时选平均 RSSI 低的。主机在 F 上发 CHANNEL，远端发出 CHANNEL_ACK 后换过去；主机收到 ACK 后也换过去并在新信道上 PING（至多 30 ms）确认。CHANNEL 每 4 次没有 ACK，主机就到目标信道上 PING 一次（对方可能已换过去、只是 ACK 丢了）；100 ms 内换不成时主机把这个点拉黑，留在对方所在的信道上。

会话中，主机每 200 次往返看一次重发：多于 10 次，或一条命令连发 3 次、60 ms 内什么都没收到时，主机把当前信道和离它不到 2 MHz 的点拉黑 10 分钟，换到下一个最好的点，不成就重新找对方：先试它可能留着的数据信道，再试 F。信道锁定时不换；连发 3 次都没收到时，在 F 或锁定的信道上复位射频。只有主机扫描。远端在数据信道上 2.5 s 没收到主机的包（同样不算执行命令的时间），或会话结束时，回到 F；会话结束的 PING（会话号 0）在数据信道上重发到远端应答。

几对探针可以同时工作：它们共用 F，靠 CRC 初值和链路地址区分彼此的包。主机在 F 上每 3 ms 左右发一次 PING，间隔里加一段由时间和 CRC 初值算出的偏移（至多约 1 ms），两对不会一直同时发送。配对时所有探针都用默认身份，彼此听得到，所以同一时间只配对一对。几对同时工作的行为由主机测试（2 到 4 对）检查，两块探针之间的隔离实测过，还没有在多对探针上实测。
