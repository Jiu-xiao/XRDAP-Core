# XR-DAP 链路帧与 XR 厂商扩展

[English](protocol.en.md)

本文说明 XR-DAP 系列探针（XRDAP-ESP、XRDAP-F103C8、XRDAP-CH32V307）与上位机之间的协议：XRDAP-ESP 在串口和 TCP 上传输 CMSIS-DAP 包时使用的帧格式，全系列都实现的 XR 厂商扩展命令（协议版本 2；0x80 到 0x85 为数据命令；0x86 为 Wi-Fi 配置，仅 XRDAP-ESP）和同一时间只有一条传输拥有探针的规则，探针的身份信息和 mDNS 广播，ESP32-C3 的 USB 口上 DAP 链路与命令行的分流，USB/IP 虚拟设备，以及 USB 主机要注意的零长度包。USB 上的 DAP 包按 CMSIS-DAP v2 的 Bulk 端点收发，没有额外的帧。这些规则在本仓库的 `xrdap/` 里实现：串口帧在 `xrdap/serial/`，会话主人在 `xrdap/session/`，厂商扩展在 `xrdap/vendor/`。

目录：1 串口帧；2 TCP 帧；3 XR 厂商扩展（3.1 规则与会话主人，3.2 状态与回复空间，3.3 条目，3.4 命令，3.5 采样，3.6 SWD 访问，3.7 0x86，3.8 字节示例）；4 探针身份与发现（DAP_Info、mDNS）；5 ESP32-C3 的 USB 口；6 USB/IP 虚拟设备；7 USB 主机的注意事项。

所有整数都是小端。十六进制示例中的空格只为易读。

## 1. 串口帧

串口帧与 libxr 的 Topic 打包帧格式相同。固件端由本仓库的 `xrdap/serial/`（`Framer` 拼帧、`SerialLink` 收发）实现，电脑端由 XRDAP-Host 的 `xrdap` 库（`transport::serial`）实现。

```
prefix 0x5A(1) + data_len(3) + topic_crc32(4) + timestamp_us(6) + version(1) + header_crc8(1) + payload(data_len) + crc8(1)
```

| 字段 | 内容 |
|---|---|
| prefix | 固定 `0x5A` |
| data_len | payload 的字节数，24 位 |
| topic_crc32 | topic 名的 CRC32。请求 topic 为 `dap_req`（`0xDC8309C5`），响应 topic 为 `dap_resp`（`0x89E1A688`） |
| timestamp_us | 48 位。探针在响应里填自己的微秒时间；请求填 0，探针不读取 |
| version | 固定 `0x01` |
| header_crc8 | 前 15 字节的 CRC8 |
| payload | `n(2) + DAP 包(n)`，n 为 DAP 包的字节数，不补零 |
| crc8 | 帧头和 payload 的 CRC8 |

CRC8 为反射多项式 `0x8C`、初值 `0xFF`；CRC32 为反射多项式 `0xEDB88320`、初值 `0xFFFFFFFF`、结果不取反（`"123456789"` 的值为 `0x340BC6D9`）。

例：请求 `DAP_Info(0xFF)`（查询包长，DAP 包为 `00 FF`）的完整帧：

```
5A 04 00 00 C5 09 83 DC 00 00 00 00 00 00 01 B1 02 00 00 FF 32
```

探针按以下规则解析：

- 帧头 CRC8 错、version 不是 1、topic 不是 `dap_req`、data_len 小于 2 或大于 2 + 包长（DAP_Info 报告的包长）时，丢弃当前候选帧，从缓冲里的下一个 `0x5A` 重新开始解析。
- 尾 CRC8 错时同样丢弃并重新同步。
- n 大于包长或 n + 2 大于 data_len 时丢弃该帧，不回响应。
- 被丢弃的请求没有响应，由上位机按超时处理。`xrdap share` 在响应超时（`--timeout-ms`，默认 2000 ms）内等不到探针的响应，或与探针之间的串口、USB、TCP 读写出错时，结束这个调试工具的连接并报告原因。`DAP_TransferAbort`（0x07）照常转给探针，按 CMSIS-DAP 没有响应，`xrdap share` 不向调试工具回任何内容；经串口时探针回的 n 为 0 的帧由上位机丢掉。

请求和响应一一对应。上位机每次发一个请求，收到响应后再发下一个。没有响应内容的命令，响应帧的 n 为 0。

固件的波特率为 4 000 000（XRDAP-ESP 的 S3 版 `firmware/esp32s3/main/config.hpp` 的 `kSerialBaud`；C3 版走 USB Serial/JTAG，波特率不起作用），8 位数据、无校验、1 位停止位、无流控。

串口没有连接和断开的概念。串口作为会话主人时，5 秒内没有任何请求即结束会话，见 3.1 节。

## 2. TCP 帧

探针的 TCP 3241 端口和 `xrdap share openocd` 的监听端口使用同一种帧，与 OpenOCD 的 `cmsis-dap backend tcp` 一致：

```
"DAP\0"(4) + 长度(2) + 类型(1) + 保留(1) + DAP 包
```

类型为 1 表示请求，2 表示响应；保留字节填 0。长度是后面 DAP 包的字节数。

- 同一时间只服务一个客户端，请求按顺序执行并应答。客户端断开时结束 TCP 的会话（3.1 节）。
- 探针收到的帧头无效（magic 不对、类型不是 1、长度为 0 或大于 1024）时关闭连接。
- 没有响应内容的命令（例如 `DAP_TransferAbort`）不回 TCP 帧。
- `xrdap share openocd` 把 TCP 帧去掉 8 字节头后交给探针（经串口时换成串口帧），响应反向转换，不解析 DAP 内容。客户端断开后，它向探针发送一次 `84 00`（停止采样）。

## 3. XR 厂商扩展

本节是协议版本 2，不兼容版本 1：版本 1 的 SUB_SET 和 SUB_CTRL 开始已经合并为 SUB_START，INFO 不再报告访问耗时。上位机先发 INFO，版本不是 2 时不使用扩展。

### 3.1 规则

- 命令放在 CMSIS-DAP 的厂商命令区：0x80 到 0x85 为数据命令（3.2 到 3.6 节），0x86 为 Wi-Fi 配置（3.7 节，仅 XRDAP-ESP）。USB、TCP、串口、无线使用同一种包。
- 探针不支持的命令响应只有一个字节 `0xFF`，这是 CMSIS-DAP 的标准行为。上位机发送 INFO 得到 `FF` 时，即可判断探针没有实现扩展。
- 只支持 SWD。目标按小端处理，数值就是目标内存里的原始字节。
- 变量地址由上位机解析（符号表、DWARF），探针只处理地址。
- 使用扩展命令前，上位机要先用 `DAP_Connect` 以 SWD 方式连接（port 为 0 或 1），并确认目标可访问。探针不替上位机连接；本会话里还没有连接时，READ、WRITE、SUB_START 返回 0x04。`DAP_Disconnect` 或会话结束之后都要重新 `DAP_Connect`。
- 用过 READ、WRITE 或采样之后，上位机必须把 DP SELECT、AP CSW、TAR 当作未知，重新写入。OpenOCD 会缓存这些寄存器，所以扩展命令和 OpenOCD 不在同一个连接里混用。

#### 会话主人

同一时间只有一条传输（USB、串口、TCP、无线远端）拥有探针和 SWD，这条传输叫会话主人。没有主人时，第一条执行 `DAP_Info` 以外命令的传输成为主人，开始一个会话。此后别的传输发来的命令一律回“忙”，不执行：

| 命令 | 回复 |
|---|---|
| `DAP_Info`（0x00） | 照常执行 |
| `DAP_ExecuteCommands`（0x7F）、`DAP_QueueCommands`（0x7E） | 容器本身照常处理，里面的每条命令各自按本表回复 |
| 其他标准命令 | `命令号 FF`（DAP_ERROR） |
| 0x80 到 0x9F 的厂商命令 | `命令号 05`（忙） |

回复空间只剩 1 字节时回一个 `FF`，没有空间时不回。

会话在以下情况结束，之后任何传输都可以成为新的主人：

| 情况 | 结束的会话 |
|---|---|
| 主人发出 `DAP_Disconnect` | 主人的会话 |
| TCP 客户端断开、串口链路停止 | 这条传输的会话 |
| USB 总线复位（拔出或主机复位） | USB 的会话 |
| 5 秒内没有收到任何串口请求 | 串口的会话 |
| 无线会话号变化或为 0，或超过租期没有 ping | 无线远端的会话（XRDAP-CH32V307） |

串口作为主人时，上位机要至少每 5 秒发一个请求（SUB_READ 即可）。

#### 采样

采样归开始它的会话所有：

- 从开始采样到停止，只接受 `DAP_Info`（0x00）、`DAP_HostStatus`（0x01）和 0x80 到 0x86。其他命令一律只回一个字节 `0xFF`，不执行。
- READ、WRITE 在采样期间可以使用，它们和采样轮流占用 SWD，可能使采样出现跳拍。
- 采样在收到 SUB_CTRL 停止（`84 00`）或开始它的会话结束时停止。停止后缓冲里的帧保留，下一个会话仍可以用 SUB_READ 读走，直到下一次 SUB_START 或清空。

### 3.2 请求、响应和状态

请求为 `命令字节 + 参数`；响应为 `命令字节 + 整体状态 + 数据`，命令字节原样回显。整体状态不为 0 时响应只有这两个字节，SUB_READ 的 0x02 除外（见 3.4 节）。

请求长度与命令里的计数字段对不上时返回 0x01，不执行。

回复空间：每条厂商命令执行前，探针先按请求算出回复要多少字节，与这一次能写的空间比较。空间是 DAP_Info 报告的包长（XRDAP-ESP 和 XRDAP-CH32V307 为 1024 字节，XRDAP-F103C8 为 512 字节）；在 `DAP_ExecuteCommands` 里是这个包里还没用掉的部分。厂商命令可以放进 `DAP_ExecuteCommands` 和 `DAP_QueueCommands`，与 CMSIS-DAP 参考实现相同；容器里的命令首尾相接，每条的长度由它自己的内容得出（READ、WRITE、SUB_START 按条目数和条目，INFO 1 字节，SUB_CTRL 2，SUB_READ 3，0x86 按操作：查询 2、保存 3 + ssid_len + 1 + pw_len、清除 3），算不出长度的容器整个回 `7F FF`。空间不到 2 字节时只回一个 `FF`；放不下整条回复时回 `命令号 03`；两种情况都不执行，也不写出给定的空间。READ 的回复为 3 + Σ(3 + size) 字节，WRITE 为 3 + 3 × count，INFO 为 22，SUB_START、SUB_CTRL 为 2，SUB_READ 至少 24。

| 整体状态 | 含义 |
|---|---|
| 0x00 | 成功；各条目的结果看条目状态 |
| 0x01 | 参数非法：长度对不上、计数为 0、size 不是 1/2/4/8、解引用次数大于 8、period 为 0、div 为 0 或 phase ≥ div、flags 保留位非 0、SUB_CTRL 的 op 未定义 |
| 0x02 | 状态不允许：采样中再发 SUB_START；SUB_READ 时没有在采样（回复照样带数据） |
| 0x03 | 资源不足：条目数超过 32、回复放不进剩余空间、一次采样用到超过 8 个不同的 AP、所有条目都到期的一帧放不进缓冲 |
| 0x04 | 没有连接目标：本会话还没有 `DAP_Connect`，或读取 AP 的 CSW 失败 |
| 0x05 | 忙：别的传输拥有探针（3.1 节） |

条目状态（READ、WRITE 的每个条目一个字节；采样帧里只用 1 位表示成功或失败）：

| 条目状态 | 含义 |
|---|---|
| 0x00 | 成功 |
| 0x10 + k | 第 k 级（0 到 7）读指针时 SWD 返回 FAULT 或超时 |
| 0x1F | 最后一次读或写时 SWD 失败（包括写后检查到粘滞错误） |
| 0x20 + k | 第 k 级的读地址没有 4 字节对齐 |
| 0x2F | 最后访问的地址没有按 size 对齐（size 为 8 时要求 4 字节对齐） |
| 0x30 + k | 第 k 级读出的指针为 0，不再继续 |

### 3.3 条目

一个条目描述一个变量的位置，可以经过最多 8 级指针。

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | ap：MEM-AP 编号 |
| 1 | 2 | id：上位机自定，响应里原样带回 |
| 3 | 1 | size：1、2、4 或 8 |
| 4 | 4 | base：起始地址 |
| 8 | 1 | n：解引用次数，0 到 8 |
| 9 | 2×n | deref_off[i]，i16，i = 0 到 n-1 |
| 9+2n | 2 | final_off，i16 |

条目长度为 11 + 2n 字节。WRITE 的条目后面紧跟 size 字节的值；采样条目后面紧跟 `div(2)` 和 `phase(2)`；READ 的条目没有额外字段。

探针按以下步骤求出最终地址：

```
cur = base
for i in 0..n-1:
    addr = cur + sign_extend(deref_off[i])      // 32 位回绕
    addr 不是 4 的倍数     -> 条目状态 0x20+i，结束
    p = read32(addr)                             // SWD 失败 -> 0x10+i，结束
    p == 0                 -> 条目状态 0x30+i，结束
    cur = p
addr = cur + sign_extend(final_off)
addr 不是 size 的倍数（size 为 8 时按 4） -> 0x2F，结束
读或写 size 字节                                  // SWD 失败 -> 0x1F
```

n 为 0 时直接访问 `base + final_off`。base 为 0 是合法的（Cortex-M 的 0 地址有效），只有读出来的指针为 0 才算空指针。数组下标和链表遍历由上位机展开成多个条目。

### 3.4 命令

#### 0x80 INFO

请求：`80`

响应固定 22 字节：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x80 |
| 1 | 1 | 整体状态 |
| 2 | 1 | 协议版本，当前为 2 |
| 3 | 4 | 功能位：bit0 READ，bit1 WRITE，bit2 采样，bit3 8 字节访问，bit4 Wi-Fi 配置（0x86）；XRDAP-ESP 为 0x1F，其余为 0x0F |
| 7 | 2 | 一个请求或一次采样最多的条目数：32 |
| 9 | 1 | 最大解引用深度：8 |
| 10 | 4 | 环形缓冲字节数：XRDAP-ESP 为 16384，XRDAP-F103C8 和 XRDAP-CH32V307 为 4096 |
| 14 | 8 | 探针当前时间，µs |

#### 0x81 READ

请求：`81 count(1) item…`，count 为 1 到 32。

响应：`81 状态 count(1)`，然后每个条目 `id(2) 条目状态(1) value(size)`。失败的条目 value 全为 0。

#### 0x82 WRITE

请求：`82 count(1) (item value)…`，value 为 size 字节，按目标字节序。

响应：`82 状态 count(1)`，然后每个条目 `id(2) 条目状态(1)`。

条目按顺序执行，已经写入的不回滚，某个条目失败不影响后面的条目。8 字节写是两次 32 位写，不是原子的。

#### 0x83 SUB_START

一条命令带全部配置，检查通过就开始采样。探针不保存“已配置未开始”的状态。

请求：`83 period_us(4) flags(1) count(2) (item div(2) phase(2))…`

- period_us：节拍周期，大于 0。
- flags：bit0 为 0 时缓冲满后覆盖最旧的帧，为 1 时丢弃新帧；其余位必须为 0。
- count：1 到 32。

响应：`83 状态`

- 采样中再发 SUB_START 返回 0x02，正在进行的采样不受影响。
- 参数非法返回 0x01；条目超过 32 个、用到超过 8 个 AP、所有条目都到期的一帧加 2 字节长度头大于缓冲时返回 0x03。
- 本会话没有 `DAP_Connect`，或读某个 AP 的 CSW 失败返回 0x04。
- 成功时清空缓冲和两个计数器，节拍序号从 0 开始，第 0 拍立即采样。

探针不估计每帧耗时，也不因为周期太短拒绝。能否跟上只在运行时看：跳过节拍数、缓冲丢帧数和缓冲里剩余的字节数，都在每次 SUB_READ 的响应头里（3.5 节）。

#### 0x84 SUB_CTRL

请求：`84 op(1)`；op 为 0 停止，2 清空缓冲和计数器。其他 op 返回 0x01。

响应：`84 状态`

- 停止：等手头这一拍读完再回复，没有在采样时也返回 0x00。缓冲里的帧可以继续用 SUB_READ 读走。
- 清空：采样中也可以用，计数器从 0 重新累计。

#### 0x85 SUB_READ

请求：`85 max_bytes(2)`

响应头 24 字节，后面是帧：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x85 |
| 1 | 1 | 整体状态：0x00 正在采样，0x02 没有在采样 |
| 2 | 8 | 探针当前时间，µs |
| 10 | 4 | 缓冲里剩余未取的帧字节数（不含长度头） |
| 14 | 4 | 累计缓冲丢帧数 |
| 18 | 4 | 累计跳过节拍数 |
| 22 | 2 | 本次返回的帧数 |
| 24 | … | 帧 |

只返回完整的帧，帧的总长不超过 `min(max_bytes, 回复空间 - 24)`；缓冲为空时帧数为 0。状态为 0x02 时响应照样带完整的头和帧：上位机据此知道采样已经停止（例如开始它的会话结束了），继续读到剩余字节为 0 即可。两个计数器在 SUB_START 成功和 op 2 时清零。

### 3.5 采样

#### 节拍

- 节拍定时器是唯一的时钟。它的中断每个周期把节拍计数加 1，计数到达下一个要采的节拍时才唤醒采样；采样醒来时读计数，最新的节拍就是计数值 k。时基只用来给帧打时间戳。
- SUB_START 成功后计数清零，第 0 拍立即采样，此后每过一个周期一拍。
- 条目在 `(k + phase) % div == 0` 的拍被采样。div 为 1 表示每拍都采；phase 用来错开慢速条目。一拍里到期的条目按 SUB_START 中的顺序依次读取。
- 没有条目到期的拍不产生帧。

#### 帧格式

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 4 | 节拍序号 k |
| 4 | 6 | 时间戳，µs，在该拍开始读取时取得 |
| 10 | ceil(m/8) | 状态位图，m 为到期条目数；第 i 个到期条目对应第 i 位（低位在前），1 表示失败 |
| … | … | 各到期条目的值，按到期顺序，每个 size 字节，失败时全为 0 |

到期的条目由 k 和各条目的 div、phase 推算，帧里不重复列出。

- 时间戳取自 libxr 的 Timebase，是探针的单调微秒时间，48 位，与 INFO、SUB_READ 里的探针当前时间是同一个时钟。每次开始采样时时间轴不重置，节拍序号从 0 重新计；探针重启后时间轴从 0 开始。
- 一帧内的条目依次读取，同一帧的变量之间有时间差，不是同一时刻的值。
- 对齐到上位机时钟：记下 INFO 或 SUB_READ 请求前后的本机时间，取中点与响应里的探针当前时间配对，得到偏移量，误差约为半个往返时间。每次 SUB_READ 都可以顺便更新偏移量。

#### 跟上与跳拍

- 采样醒来时，从上一次采到的节拍到当前计数之间没有采的节拍都算跳过，累计到跳过节拍数；节拍序号因此出现缺口。探针不补做，也不自动降频或去掉条目。
- 一拍读到一半时下一个节拍已经到了，这个节拍不补做，等再下一个节拍。
- 每帧读完后，下一个要采的节拍至少比这一帧的节拍晚 `占用 + 间隙`，间隙为 `max(15 µs, 周期 / 8, 占用 / 4)`，占用在采样任务方式下从节拍中断唤醒采样的那一刻算到这一帧读完，包括唤醒、切换任务和取链路锁的时间（单循环的探针从开始读帧算起，中断之后的等待是主循环在做命令）；中间的节拍计入跳过节拍数。
- 因此任何周期下探针都能回应命令：两帧之间同一个核上的其他任务（DAP 命令、串口、TCP）至少有这段间隙，约占这个核 1/5 以上的时间。周期短于一帧的占用时只多出跳过的节拍，命令不会等不到 CPU。

#### 读取太慢

帧先写进环形缓冲（大小见 INFO，每帧另占 2 字节长度）。缓冲满时按 flags.bit0 覆盖最旧的帧或丢弃新帧，覆盖或丢弃的帧数累计到缓冲丢帧数，节拍序号的缺口也能看出丢了哪几拍。剩余未取字节数不为 0 时，上位机应立即再读。

每拍的字节数为 10 + 位图 + 各到期条目的 size，按 div 折算平均值后与链路的实际速度比较，即可估计带宽是否够用。

上位机按这三个量判断能否跟上，并给出建议：

| 量 | 说明 | 建议 |
|---|---|---|
| 跳过节拍数 | 增长说明 SWD 来不及 | 增大周期、增加分频、减少条目 |
| 缓冲丢帧数 | 增长说明读得太慢或链路带宽不足 | 读得更勤、增加分频、减少条目 |
| 剩余字节数 | 持续接近缓冲大小说明快要丢帧 | 同上 |

### 3.6 SWD 访问

- DP SELECT：访问 MEM-AP 时写 `ap << 24`，CSW、TAR、DRW 都在 bank 0。读 AP 的 IDR 时用 bank 0xF（寄存器 0xFC）。
- CSW：每个 READ、WRITE 命令中第一次用到某个 AP 时，以及 SUB_START 时，读一次该 AP 的 CSW；同一命令或同一次采样期间不重新读取。读出的 CSW 里 HPROT1（位 25）为 0 时，再读该 AP 的 IDR：IDR 的类别（位 16:13）为 8（MEM-AP）、类型（位 3:0）为 1、5 或 8（AHB3、AHB5、带增强 HPROT 的 AHB5）时，把 Prot 的位 24（HPROT0，数据访问）、位 25（HPROT1，特权访问）和位 29（调试主机）置 1，与 OpenOCD 的 `CSW_AHB_DEFAULT` 相同；Prot 的其余位（缓存、缓冲、安全属性）保持读出的值。别的 AP 类型（例如 AXI-AP、APB-AP）的这些位含义不同，保持原值。访问时写入 `(上述值 & ~0x37) | Size`，即清掉 Size（位 2:0）和 AddrInc（位 5:4），设置访问宽度并关闭自增。写过一次之后 AP 里的 HPROT1 已经为 1，此后不再读 IDR。
- 读一个字：写 TAR，读 DRW，再读 DP RDBUFF 得到结果。条目按顺序逐个访问。
- 写一个字：写 TAR，写 DRW，再读 DP CTRL/STAT，检查 STICKYORUN、STICKYERR、WDATAERR。
- 1、2 字节访问：CSW 的 Size 设为 8 位或 16 位，值在 DRW 中由地址低位决定的字节通道上，探针把它放到 value 的低字节。
- 8 字节：两次 32 位访问，低地址在前，不是原子的，目标运行时可能读到前后不一致的值。4 字节及以下的对齐访问是单次访问。
- WAIT 应答：沿用 `DAP_TransferConfigure` 设置的重试次数，超过算失败。
- 任何访问出现 FAULT、超时或粘滞错误后，写 DP ABORT = `0x0000001E`（STKCMPCLR、STKERRCLR、WDERRCLR、ORUNERRCLR），再继续下一个条目。
- 读写内存由 MEM-AP 完成，不需要停核。

### 3.7 0x86 Wi-Fi 配置

仅 XRDAP-ESP。经 DAP 本身（USB、串口、TCP 均可）查询、保存、清除热点参数，不需要另开串口终端。INFO 的功能位 bit4 为 1 时才支持。热点参数存放在 NVS 里（命名空间 `rmlink`，键 `wifi`），与串口命令行 `wifi set` 保存的是同一份数据。

这条命令不访问目标，也不要求先 `DAP_Connect`；采样期间同样可用。请求格式为 `86 op(1) 参数`，响应第 1 字节回显 `86`，第 2 字节为状态。

| 状态 | 含义 |
|---|---|
| 0x00 | 成功 |
| 0x01 | 参数非法：op 未定义，请求长度与 op 不符，热点名为空或超过 32 字节，密码不为空且不在 8 到 63 字节之间（WPA 密码长度） |
| 0x03 | 资源不足：NVS 读写失败，或响应缓冲放不下状态响应 |

#### op 0 查询

请求：`86 00`（长度必须为 2 字节）

成功响应：

| 偏移 | 大小 | 字段 |
|---|---|---|
| 0 | 1 | 0x86 |
| 1 | 1 | 状态 0x00 |
| 2 | 1 | 标志：bit0 Wi-Fi 已启动（保存了热点参数才会启动），bit1 已拿到 IP，bit2 这次启动时 NVS 已损坏，已擦除重建 |
| 3 | 4 | IPv4 地址，按网络字节序（`C0 A8 01 14` 即 192.168.1.20）；未连接时为 0 |
| 7 | 1 | 信号强度 RSSI，i8，单位 dBm；未连接时为 0 |
| 8 | 1 | 热点名长度 n |
| 9 | n | 已保存的热点名，没有则 n 为 0；不返回密码 |
| 9+n | 1 | 热点参数最近一次被谁清除（存在 NVS 里）：0 没有或不知道，1 板上按键，2 命令行 `wifi clear`，3 0x86 清除，4 NVS 修复 |
| 10+n | 1 | 这次启动的复位原因：0 不知道，1 上电，2 软件重启，3 看门狗，4 程序异常，5 欠压，6 其他 |

失败时响应只有 `86` 和状态两个字节。

#### op 1 保存

请求：`86 01 ssid_len(1) ssid(ssid_len) pw_len(1) password(pw_len)`

请求总长必须等于 `4 + ssid_len + pw_len`。开放网络的 pw_len 为 0。

响应：`86 状态`。状态为 0x00 时热点参数已写入 NVS，响应发出后约 0.5 秒探针重启，重启后用新参数连接热点。重启期间 USB 设备重新枚举，串口和 TCP 连接中断，上位机需要重新连接。

#### op 2 清除

请求：`86 02 A5`（长度必须为 3 字节，第 3 字节是确认字节 0xA5）。确认字节不对或缺少时返回 0x01，什么都不做，防止误发的短命令清掉热点参数。

响应：`86 状态`。状态为 0x00 时热点参数已清除，响应发出后约 0.5 秒探针重启，重启后不启动 Wi-Fi。

## 4. 探针身份与发现

### 4.1 DAP_Info 字符串

固件在 `DAP_Info` 里返回以下字符串（本仓库 `probe/probe_identity.hpp`）。有 USB 的探针，USB 设备描述符使用相同的厂商和序列号。

| Info ID | 含义 | 内容 |
|---|---|---|
| 0x01 | 厂商 | `XRobot` |
| 0x02 | 产品 | ESP32-S3：`XR-DAP-S3`；ESP32-C3：`XR-DAP-C3`；ESP32：`XR-DAP-ESP32`；STM32F103：`XR-DAP-F103`；CH32V307：`XR-DAP-V307` |
| 0x03 | 序列号 | `XRobot-XRDAP-` 加芯片唯一标识的大写十六进制：ESP 为出厂 MAC（eFuse 中的 6 字节，12 位），例如 `XRobot-XRDAP-0123456789AB`；STM32F103 和 CH32V307 为 12 字节 UID（24 位） |
| 0x04 | CMSIS-DAP 协议版本 | `2.0.0` |
| 0x05、0x06 | 目标芯片厂商、名称 | 不提供（空） |
| 0x07 | 板子厂商 | `XRobot` |
| 0x08 | 板子名 | XRDAP-ESP 与产品相同；XRDAP-F103C8 为 `STLINK-V2`；XRDAP-CH32V307 为板子名，例如 `XR-DAP-WDAP` |
| 0x09 | 固件版本 | 各固件自己的版本号 |

序列号对 USB、串口、TCP 等各种连接相同，上位机据此认出同一块探针。

### 4.2 mDNS 广播

探针拿到 IP 后在局域网上广播：

| 项目 | 内容 |
|---|---|
| 主机名 | `xrdap-` 加 MAC 后 3 字节的小写十六进制，例如 `xrdap-6789ab.local` |
| 服务 | `_xrdap._tcp`，端口为 TCP DAP 端口 3241 |
| 实例名 | 序列号，例如 `XRobot-XRDAP-0123456789AB` |
| TXT `serial` | 序列号 |
| TXT `chip` | `esp32s3` 或 `esp32c3` |
| TXT `fw` | 固件版本，例如 `0.5.5` |

OpenOCD 可以直接把主机名写进 `cmsis-dap tcp host`。上位机枚举 `_xrdap._tcp` 服务即可列出局域网内的探针，用 TXT 的 `serial` 与 USB、串口上的同一块探针对应。mDNS 启动失败只记日志，不影响 TCP 服务。

## 5. ESP32-C3 的 USB 口

ESP32-C3 的 USB 口是 USB Serial/JTAG，电脑上是一个 CDC 串口，DAP 链路（第 1 节的串口帧）和 Wi-Fi 命令行共用这个口，不需要切换模式。固件（XRDAP-ESP 的 `firmware/common/serial/serial_mux.hpp`）对每块收到的数据这样处理：

1. 先交给 DAP 链路。链路自己查找帧头 `0x5A`、校验 CRC，非帧字节直接丢弃。
2. 这一块数据执行了至少一个 DAP 帧，或者最近 2 秒内执行过 DAP 帧时，数据不交给命令行。
3. 其余数据逐字节交给命令行。命令行只在收到一行人打的命令并以回车结束后才输出；一行里出现控制字符时整行丢弃。

因此 DAP 帧和命令行的输出不会混在一起：调试工具收到的永远是 DAP 响应帧，终端里 `help`、`wifi set` 等命令照常可用。终端不要改动 DTR/RTS，否则 USB Serial/JTAG 可能复位芯片。ESP32-S3 的串口链路在 UART0 上，不做这种分流；它的命令行在 USB 的 CDC 虚拟串口上。

## 6. USB/IP 虚拟设备

探针在 TCP 3240 端口提供 USB/IP（协议见 Linux 内核文档 `usb/usbip_protocol.rst`，字段大端）。实现在 XRDAP-ESP 的 `firmware/common/net/usbip_device.hpp`，上位机 xrdap 库的 `usbip` 模块是同一个设备模型。

| 操作 | 处理 |
|---|---|
| `OP_REQ_DEVLIST` (0x8005) | 回一个设备，总线号 `1-1`，然后关闭连接 |
| `OP_REQ_IMPORT` (0x8003) | 总线号为 `1-1` 时回设备信息，之后是 URB；其他总线号回状态 1 |
| `USBIP_CMD_SUBMIT` (1) | 端点 0：标准请求和描述符；端点 1：Bulk OUT 执行 DAP 命令，Bulk IN 取响应 |
| `USBIP_CMD_UNLINK` (2) | 取消还在等数据的 IN；找到时回 -ECONNRESET，否则回 0 |

设备：

- 设备：bcdUSB 0x0210（有 BOS 时至少 2.01），类 0/0/0，EP0 包长 64，1D50:6199，bcdDevice 0x0200，字符串索引 1/2/3，一个配置。

- BOS 的平台能力 UUID 为 MS OS 2.0 的 `{D8DD60DF-4589-4CC7-9CD2-659D9E648A9F}`，Windows 版本 0x06030000，描述符集 162 字节，厂商请求码 0x20。主机用 `GET` 厂商请求（bRequest 0x20，wIndex 7）取描述符集。

DAP 命令的配对：每个 Bulk OUT 立即执行，响应排进队列（深度 4，与 DAP_Info 报的包数相同），按到达顺序交给等着的 Bulk IN；IN 先到时排队等响应。没有响应的命令（DAP_TransferAbort）不占 IN。队列满时 URB 回 -EPIPE。

一个命令引起的回复（OUT 的回复和配上的 IN 响应）合成一次 `send()`。分两次发时，第二段要等对方的延迟 ACK，每个来回都慢很多。

## 7. USB 主机的注意事项

USB 全速的 Bulk 包是 64 字节。请求长度正好是 64 的整数倍（128、192 字节等）、又小于 DAP 包长时，OUT 传输没有短包来标志结束，探针会一直等下去，表现是这个请求没有响应、之后的响应还会错位。主机发完这样的请求后要再发一个零长度包。8 个条目的 SUB_START 正好 128 字节，最容易遇到。`xrdap` 已经处理；自己用 libusb、pyusb 写客户端时要加。接收时 IN 请求的长度要取端点最大包长的整数倍（不小于 DAP 包长）。
